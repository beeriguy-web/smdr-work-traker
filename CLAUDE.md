# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

This repository contains a single self-contained HTML file, `index.html`, implementing an internal work-order form ("טופס הזמנת עבודה פנימית") for שמדר טכנולוגיות בע"מ (Shmadar Technologies Ltd.), an Israeli company. The UI is entirely in Hebrew and right-to-left (`dir="rtl" lang="he"`).

There is no build system, package manager, bundler, or test suite — the entire app is one HTML file with inline `<style>` and `<script>` blocks, loading Bootstrap 5.3.2 (RTL build) from a CDN. There is nothing to install or compile.

## Running / testing changes

- Open `index.html` directly in a browser (or serve it with any static file server, e.g. `python3 -m http.server`) — there is no dev server, no `npm install`, and no test command.
- There is no linter or automated test suite configured. Verify changes manually in a browser: fill out the form, and exercise "PDF" and "שלח במייל" (send email).
- When testing the PDF flow, note that `downloadPDF()` opens a new browser window/tab and calls `window.print()` — popup blockers can suppress this.

## Architecture

Everything lives in `index.html`, organized top to bottom as:

1. **`<style>`** — all CSS, including a `@media print` block that hides interactive chrome (toolbar, buttons, hints) and forces color backgrounds when printing/exporting to PDF.
2. **Markup** — a fixed toolbar, then a single `.form-card` containing the work-order form: meta row (to/from/date), client & project fields, dynamic contacts list, work details (including the `f-jobname` "שם העבודה" textarea — see below), items table, free-text description, and an approval section with an HTML5 canvas signature pad. Note: the "project" field's element id/JS variable name is still `f-site`/`site` (historical — the on-screen label was renamed from "אתר" to "פרויקט", but the id was left alone to avoid touching every reference).
3. **`<script>`** — all application logic, in roughly this order:
   - **Signature pad**: mouse/touch drawing on `#sig-canvas`; `getSignatureDataUrl()` returns `null` if the canvas is still blank (compared against a fresh blank canvas) so an empty signature isn't embedded in output. The canvas is *not* blank by default: `drawDefaultSignature()` draws a pre-scanned stamp+signature image (`SIGNATURE_STAMP_SRC`, a base64 JPEG data URI) onto it on page load and whenever `newForm()` resets the form, since the approver (`f-appr-by`) is always the same person. "מחק חתימה" (`clearSignature()`) still just clears the canvas to blank for the rare case of a different/fresh signature — it does not restore the default image.
   - **`CONTACTS_DB`** (index.html:536): starts as an empty `{}` and is populated asynchronously from a Google Sheet via `SHEETS_API` (a Google Apps Script Web App URL) — `fetch(SHEETS_API)` maps returned rows into the same `{n: name, e: email, p: phone}` shape keyed by company name. If that fetch fails (offline, script down, etc.), the `.catch()` falls back to `_OLD_CONTACTS_DB`, a hardcoded snapshot of the original contacts data kept as a single very long line right after it — when reading or grepping this file, target specific line ranges or use `Grep` rather than reading the whole file at once. `saveNewContact(company, name, phone, email)` POSTs a new contact to the same `SHEETS_API` endpoint and appends it to the in-memory `CONTACTS_DB` immediately (optimistic — happens regardless of whether the POST succeeds), and shows a `toast()` warning if the POST fails (network error or non-2xx response) so a broken Sheets connection isn't silently invisible. `saveNewContactsFromForm()` (called at the start of both `downloadPDF()` and `sendEmail()`) auto-saves the current client + any contacts typed into the form that aren't already present under that client in `CONTACTS_DB` — this is how new companies/contacts typed by hand end up persisted to the Sheet without an explicit "save contact" button. `CONTACTS_DB` is the data source for both the client-name and per-contact autocomplete dropdowns (`onClientInput`, `onContactInput`), which both wire up `acNavigate(input, box, onSelect)` on first use (guarded by `input._acInit`) to add arrow-key/Enter/Escape keyboard navigation over the `.ac-item` results.
   - **Multi-contact management**: `formContacts` array (max 5 entries) backs dynamically rendered contact rows (`renderContacts`, `addContact`, `removeContact`); `syncContactsFromDOM`/`collectContacts` read current values back out of the DOM before adding/removing rows or switching client (since inputs are re-rendered via `innerHTML`).
   - **Items table**: `addRow()`/`removeRow()` manage table rows for line items (description, quantity, notes); `collectRows()` reads them back for PDF/email output. Row numbering is recomputed from `tbody.rows.length`.
   - **`newForm()`**: resets all fields to defaults (including `f-jobname`, re-adding 2 blank item rows, and clearing the signature) after a `confirm()` prompt.
   - **`jobName()`**: returns `f-jobname` if filled, else falls back to the first item row's description, then the client name, then a generic default. This single value is reused everywhere a "job name" is needed so it stays identical across surfaces: the PDF's suggested filename (`pdfFileName()`, which additionally strips filesystem-unsafe characters and HTML-escapes the result), the "שם העבודה" row in the PDF's work-details table (`buildPdfHTML`), and the `desc` field pushed to מעקב עבודות (see below).
   - **PDF export** (`buildPdfHTML`, `downloadPDF`): builds a standalone print-friendly HTML document as a string (mirroring the on-screen form's content but with inline styles, since it's rendered in a separate `window.open('', '_blank')` document), writes it via `document.write`, and triggers `window.print()` after a short delay. Note the `sp()` helper replaces regular spaces with non-breaking spaces (` `) in dynamic text — this works around `html2canvas`/print rendering collapsing spaces. The popup's `<title>` is set via `pdfFileName()` — browsers that support "Save as PDF" from the print dialog use the document title as the suggested filename.
   - **Email export** (`buildEmailBody`, `sendEmail`): builds a plain-text summary and opens a `mailto:` link addressed to `gal@smdrtech.co.il` (the PDF itself is not attached automatically — the mailto body tells the recipient to expect the PDF as a separate manual attachment). `sendEmail()` also calls `pushToWorkTracker()` (see below) — the work-traker entry is only created on "שלח במייל", not on "PDF".
   - **`copyLink()`**: copies the current page URL (stripped of query params) to the clipboard so the blank form can be shared with other employees.
   - **מעקב עבודות integration** (`pushToWorkTracker`): שמדר טכנולוגיות also runs a separate GitHub Pages app, `beeriguy-web/work-traker` (live at `https://beeriguy-web.github.io/work-traker/`), for tracking jobs sent to the technical office. Because both apps are served from the same origin (`beeriguy-web.github.io`, different paths), this form integrates with it with no backend — by writing directly into work-traker's own `localStorage` keys (`wt_v4`, the jobs array, and `wt_cnt4`, its running counter), matching its job shape exactly: `{id, num, date:'DD/MM/YY', cust, proj, desc, status:'open', notes}`. `pushToWorkTracker()` runs only from `sendEmail()`, and **always creates a brand-new entry — deliberately no deduplication**, since the technical office assigns its own unique per-job number and the same `f-wnum` legitimately repeats across different jobs. Pushed entries are tagged `notes: 'נשלח מהטופס'` (plus the work order number, if set) so they can be told apart from manually-added work-traker entries, e.g. when exporting to Excel from there. The toolbar's "📊 מעקב עבודות" tab now shows the work tracker inside this page (view `wt`, an `<iframe>` of `avodot.html` – see the cloud.js section; it used to be `https://beeriguy-web.github.io/work-traker/`) — this replaced an earlier, purely-local "יומן עבודות" (job log) modal/CSV-export feature that has been removed entirely in favor of this shared, cross-device tracker.

## Key conventions

- Keep all user-facing strings in Hebrew, RTL-correct, and consistent with the existing tone/terminology (e.g. "מספר עבודה", "מועד אספקה").
- Preserve the `PR<number>/@...` format for work order numbers (`wnum()`), and `DD/MM/YYYY` formatting for dates (`fmtDate()`), which are used in the printed PDF. On screen, the `f-wnum` input's `/@...` suffix sits in an `input-group-text` span placed *before* `PR` in DOM order (not after) — with `dir="rtl"`, the first flex child renders rightmost, so this ordering is what puts `/@...` visually adjacent to the right of the number field while `PR` reads first on the left. Wherever `wnum()`'s return value is embedded as plain text inside an RTL-styled element (the PDF's `buildPdfHTML` table cell), wrap it in `<span style="direction:ltr;unicode-bidi:isolate;">` — otherwise the browser's bidi algorithm reorders the mixed Latin/digit/punctuation string (e.g. rendering `PR23-07/@...` as `...@/PR23-07`).
- When editing the PDF template (`buildPdfHTML`), remember it's a fully separate inline-styled document (not reusing the page's CSS classes) — any style changes made to the on-screen form must be mirrored there manually if they should also appear in the printed/PDF output.
- `_OLD_CONTACTS_DB` (the offline fallback for `CONTACTS_DB`) is real customer/contact data (names, phone numbers, emails). Treat edits to it carefully and avoid introducing malformed JSON, since a syntax error there breaks the entire script.
- Before editing this file in a new session, make sure you're working from the latest `main` — this repo has already had one incident where a session with a stale local copy of `index.html` was used to add a couple of functions and got pushed, silently reverting a batch of unrelated work (theme, logo, job log, signature) that had landed on `main` in the meantime. `git fetch && git log origin/main -1` before starting is worth the ten seconds.
- The theme color is `#BC2129` (with lighter/darker variants like `#D6343E` and `#FBE4E4`), sampled directly from שמדר טכנולוגיות's live site (smdrtech.co.il) to match company branding — used consistently across the toolbar, headers, focus/hover states, and the PDF template. Keep any new UI elements consistent with this palette rather than introducing new colors.
- The company logo (`.header-logo` in the on-screen `.form-header`, and its inline-styled twin in `buildPdfHTML`'s header) is a base64-encoded PNG data URI embedded directly in the markup — cropped from a company letterhead image, then converted from red-on-white to white-on-transparent (thresholded alpha, not a straight recolor) so it reads correctly against the red header background. Not a vector asset, so avoid re-scaling it much larger than its current ~46px display size. As with all PDF-template styling, keep the two copies in sync if the logo or its layout changes.
- The PDF export popup's own `<style>` block (inside `downloadPDF()`) must keep `-webkit-print-color-adjust: exact !important; print-color-adjust: exact !important;` on `*` — without it, browsers silently drop all background colors (header, section labels, table headers) when printing/saving as PDF unless the user manually enables "background graphics" in the print dialog, which most people don't. This is separate from the main page's own `@media print` rule of the same kind (index.html:270) — the popup window is a fully separate document and doesn't inherit the main page's styles.

## Trackers in the Google Sheet – `cloud.js` (added 2026-11-21)

Its old per-app Sheets setting is disabled; it syncs through `cloud.js`. The old repo/site `beeriguy-web/work-traker` is no longer used by anything (the user removed his shortcut to it and chose to leave the repo as is, not delete it) – it does NOT sync to the Sheet, so never point anything back at it; if a future change would depend on it, tell the user first. ## Shared contacts – `contacts.js` (added 2026-11-23)

- **One contacts store for all four forms.** `contacts.js` (`window.SmdrContacts`, included by index.html, hiarchut.html, siyur.html – bump `contacts.js?v=` in all three on change) loads the Sheet (`SHEETS_API`), keeps `SmdrContacts.db` = `{company:[{n,p,e,r}]}` (r = role), caches it in `localStorage['smdr_contacts_cache_v1']`, and broadcasts every change on `BroadcastChannel('smdr_contacts')`, so a contact added in one form appears in the others (iframes included) immediately, without reload. index.html's `CONTACTS_DB` is the same object; hiarchut's `DB.clients` and siyur's `CL` are rebuilt from it on `onChange`.
- **Saved immediately**: `SmdrContacts.save(company, c)` is called when a contact row is added/left (work order, handover), when a contact is added or its role/phone/mail edited (summaries, site visit) – not only on PDF/mail. Saves are queued sequentially. Contacts with an `@smdrtech.co.il` address are never saved to the Sheet.
- **Company names**: `SmdrContacts.resolve(typed)` maps a typed/partial name to the exact Sheet company (exact → normalized → unique substring). Client fields (`f-client`, `hv-client`, hiarchut and siyur `client`) resolve on blur; an unknown company shows "חברה חדשה – תישמר במאגר בשם הזה. כתוב את השם המלא."
- **Roles**: shared list `SmdrContacts.ROLES`; stored in column E "תפקיד" of the contacts sheet. A new role overwrites the previous one (people change roles between projects).
- **Apps Script v3** (`apps-script/Code.gs`): GET returns `role`; contact POST is an upsert (match normalized company+name → update phone/email/role with non-empty values; else insert), under `LockService`. The client detects v3 by the presence of the `role` key (`SmdrContacts.roleSupport`); with the old script it only POSTs brand-new contacts (no updates), so no duplicate rows are created.
